# Security status

|---|---|

Vaultex is **unaudited pre-alpha research software. Use it on testnets only, and never with real funds.**

This page lists the known security limitations **by category, each with its planned fix**. It contains no exploit details and no pointers into the code. Detailed advisories come only after a fix ships, affected users have had time to re-key, and a grace period has passed. A category-level GitHub Security Advisory with re-key guidance is planned ([ROADMAP](docs/ROADMAP.md) M5 #3).

---

## What to do now

- Do not use any version of Vaultex with real funds.
- Do not send funds to an address that Vaultex exported for a chain marked Experimental in the [README support matrix](README.md#support-matrix), or to a P2WPKH address shown for a FROST-TR wallet. Such addresses may be unspendable.
- Treat every key produced by the hand-rolled threshold-ECDSA engines (GG20, CGGMP21, Stark-curve) as exposed. If such a key controls value on any network, move the value to a key generated by well-reviewed software, then destroy the old shares.
- Never run the single-process CLI or the local dev stack with real funds.

## Known limitations

**Status:** **Open** = no part of the fix is merged · **In progress** = part of the fix is merged · **Fixed** = the whole fix is merged, with a named test or CI run, and the version is given.

Milestone numbers refer to [docs/ROADMAP.md §4.3](docs/ROADMAP.md#43-milestone-definitions).

| # | Category | Affects | Status | Planned fix | Milestone |
|---|---|---|---|---|---|
| 1 | **Affected scheme classes.** The hand-rolled threshold-ECDSA engines are unsound by design. Sr25519 and BLS signing are not threshold signing | GG20, CGGMP21 and Stark-curve threshold ECDSA, with their refresh and reshare; Sr25519; BLS; every chain that signs with them | Open | Interim: release builds refuse key generation, every legacy scheme and every mainnet network. Then the hand-rolled engines are removed from builds (delete or quarantine: decision ADR-03), after a pre-cut tag and retirement of the legacy keys. Any future ECDSA engine will be an adopted, pinned library under independent review (decision at the G-MPC gate) | M5 #4–5; M8 #1–3 |
| 2 | **Transport confidentiality and peer authentication during key generation** | Messages between MPC nodes over the message bus, for every scheme including FROST | Open | Interim: release builds refuse key generation. Then transport v2: sender authenticated and bound to its party index, per-recipient encryption under identities pinned in each node's config, bus TLS with per-node credentials and subject ACLs, size limits checked before parsing, and an adversarial test suite run as a required CI job | M5 #5; M8 #4–5 |
| 3 | **Control-plane freshness** and trust concentrated in one gateway key and one deployment secret | Control messages from gateway to nodes (key generation, signing, freeze); the gateway's signing key | Open | Control plane v2: freshness and persisted replay checks on every node, gateway keys split by purpose, per-node secrets, and unfreeze only locally or by an M-of-N admin message | M8 #4, #6; M11 |
| 4 | **Unenforced signing policy.** Signers do not independently verify what they sign; the gateway asserts the policy result | MPC node signing path; gateway; the policy, approval and velocity modules (library code only) | Open | Interim: release builds refuse digest-only signing requests. Then a verifier kernel that decodes the exact transaction and enforces a quorum-signed policy bundle and k-of-n approvals, which every node runs before it signs | M5 #5; M6; M9 #1–5 |
| 5 | **Unsafe deposit addresses.** Addresses exported by pre-cut versions for unimplemented chains, and P2WPKH addresses shown for FROST-TR wallets, may be unspendable | CLI and REST address export for every chain marked Experimental in the README; P2WPKH addresses shown for FROST-TR wallets | Open | Chain gating: the CLI and REST API never serve placeholder or unspendable addresses; the category-level advisory reaches existing clones and forks | M5 #1, #3–5 |
| 6 | **Test-only cryptographic parameters can reach builds** | Workspace builds; tests and CI evidence | Open | A CI job builds the node and gateway exactly as shipped and fails if any test parameter or experimental feature is linked; a release build that links test parameters fails to compile or refuses to start. Tests use cached production-size parameters, never reduced ones | M5 #8; M8 #7 |
| 7 | **Key shares co-located by demo tooling** | The single-process CLI (it runs every party in one process); the boot-node wrapper | Open | The boot-node wrapper never mounts a keystore that holds more than one party's shares; the single-process CLI moves behind a non-default experimental feature | M5 #4 |
| 8 | **Custom, unreviewed gateway authentication** | Gateway authentication: key-exchange handshake, session tokens, mTLS, bearer tokens | Open | Interim: the freeze switch blocks every gateway path that can move value. Then replacement by in-process rustls mTLS plus initiator and admin signatures that each node verifies (decision ADR-09) | M5 #5; M9 #4 |
| 9 | **No key backup, recovery or durable state.** Losing nodes or restarting the gateway can lose wallets | Key store; gateway wallet registry (held in memory) | Open | Each node keeps registry, replay, velocity, freeze and receipt state in an fsync'd, hash-chained log; the gateway becomes a relay rebuilt from signed node registries; backup, restore and recovery drills | M9 #3; M11 |
| 10 | **CI, release and dependency controls** | CI workflows; release workflow; dependency lockfile | In progress | Done: every CI step runs under bash with pipefail, tests gate on cargo's exit code, actions are pinned by commit SHA, workflow tokens are read-only by default, and runs are grouped by ref. Pending: a failing canary PR proven to turn CI red, branch protection and CODEOWNERS, auto-release disabled, patched dependencies with every suppressed advisory re-reviewed and a daily audit job, then signed reproducible releases | M5 #6–7; M7 #6; M11 |

## Assurance

- No independent audit, penetration test or external review of Vaultex has taken place. The `v0.1.0-audit` tag marks an internal audit-preparation snapshot.
- [docs/SECURITY_FINDINGS.md](docs/SECURITY_FINDINGS.md) and [docs/SECURITY_AUDIT_AUTH.md](docs/SECURITY_AUDIT_AUTH.md) are internal notes written by AI agents during development. Their "resolved" statuses do not cover the categories above.
- The roadmap proposes paid limited evaluations at M6 and M7, then an independent audit and penetration test at M10, paid for only once a user has committed (decision ADR-08).

## Controls present in the code

These exist in the code today. They are experimental and not independently reviewed, and none of them offsets the limitations above.

| Control | Detail |
|---|---|
| Key store encryption at rest | Argon2id (64 MiB, 3 iterations, 4 lanes) derives an AES-256-GCM key, with a random 32-byte salt and a random 96-bit nonce per write |
| Key-share bytes | Each stored key share holds its secret bytes in a zeroize-on-drop buffer |
| Memory safety | No `unsafe` code in `crates/` or `services/` |
